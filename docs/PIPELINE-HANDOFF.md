# Pipeline handoff — showing an external tool's stages in BitWave

**Status: proof-of-concept scaffold (2026-11-23).** No schema, toolset or UI
change; this note plus `tools/pipeline-doc.mjs` describe how a program like
machine.py hands its settled registers to BitWave for display.

Companion to [`FREE-FRAMES.md`](FREE-FRAMES.md) (the container),
[`DATASET-LIFECYCLE.md`](DATASET-LIFECYCLE.md) (stepping) and
[`CONSTRAINTS.md`](CONSTRAINTS.md) (what is law vs provisional).

---

## 1. The idea

BitWave should not run a curve, a hash or a compression. It is the *display*
half of a two-part contract:

```
   external tool                         BitWave
   ─────────────                         ───────
   compute stages  ──►  stage table  ──►  registers  ──►  waveforms
   (Python, Rust, JS)     (CSV/JSON)      (free frames)     (lanes show deltas)
```

The external tool keeps its own correctness. BitWave only ever receives
**settled registers** plus the provenance strings (`label`, `sourceNote`) that
say where each one came from. That is the same boundary the D52 Free Frames
slice was built for: an agent runs NumPy or a curve library outside, then maps
the outputs into registers it can show.

The "pre-flight awareness" part is the **capability report**: before running a
long computation, ask the scaffolder what a stage list would look like. It
answers with the width each stage needs, how much of the register is padding,
which stages can be chained, and what will not fit.

## 2. What BitWave can represent

| dimension | envelope | consequence for a handoff |
|---|---|---|
| register width | one shared `N` ∈ {8, 16, 32, 64, 128, 256} | a pipeline whose stages have different natural widths is padded to the widest **supported** width |
| stages | ≤ 16 free frames (`F1`–`F16`) | a longer chain is split across documents (e.g. "pre-hash" / "address") |
| deltas | ≤ 8 lanes, `Z = A op B`, `op` ∈ `and or xor add sub` | each lane compares two frames; XOR is the Hamming-delta view |
| expressions | `+ - * / % & \| ^ ~ << >>`, `floor ceil round abs min max`, frame names, `N`, `log.<frame>` | a stage can be a deterministic function of others instead of a literal |
| provenance | `label` ≤ 48 chars, `sourceNote` ≤ 160 chars | carry the function name and its arguments, not just the value |
| dataset | one table, rows stepped with the stepper / `stepDataset` | rows are projects or keypairs; stepping re-binds every dataset-bound frame |
| motion | LFO animates one register; Record captures rows | LFO is per-register polish, not a project cycler |

**Not representable:** a 160-bit register as 160 bits (pad to 256), more than
16 standalone stages per document, more than 256-bit words (split the word), or
any execution of your code inside BitWave.

## 3. The two files

### 3.1 Stage table (`CSV`)

One row per project/keypair, one column per stage. Natural hex lengths are
fine — shorter values are zero-padded when they reach a register.

```csv
key,x,y,sha256,hash160,b58_payload
0000…0001,79be…1798,483a…d4b8,0f71…0554,751e…3bd6,00751e…38d3
```

`examples/btc-p2pkh.csv` is generated by `tools/p2pkh_chain.py`, which also
asserts the published check vector (private key 1, compressed →
`1BgGZ9tcN4rm9KBzDn7KprQz87SZ26SAMH`).

### 3.2 Pipeline spec (`*.pipeline.json`)

Small and declarative; it says how stages map, never what they compute.

```json
{
  "title": "secp256k1 → P2PKH (compressed)",
  "width": 256,
  "dataset": "btc-p2pkh.csv",
  "stages": [
    { "frame": "F1", "column": "key",   "label": "k",     "sourceNote": "private key" },
    { "frame": "F2", "column": "x",     "label": "x(kG)", "sourceNote": "secp256k1 affine x" },
    { "frame": "F5", "column": "hash160", "label": "hash160", "sourceNote": "ripemd160(sha256)" }
  ],
  "lanes": [
    { "lane": "1", "a": "F4", "b": "F5", "binop": "xor", "note": "digest → hash160" }
  ],
  "view": { "activeFree": "F2" }
}
```

A stage uses either `column` (dataset-bound, cycles with the rows) or `hex`
(a fixed literal, for a comparison document). A lane's `a`/`b` are free-frame
names (`F1`–`F16`); the scaffolder routes them into the lane's operands.

## 4. The scaffolder

```powershell
node tools/pipeline-doc.mjs `
  --pipeline examples/btc-p2pkh.pipeline.json `
  --out      examples/btc-p2pkh.bitwave.json `
  --base     "file:///C:/path/to/bitwave-v2.html"
```

It prints the capability report and writes the schema-5 document:

```
secp256k1 → P2PKH (compressed) — 256-bit, 6 stages, 3 lanes
  F1  k           column:key        4 bits, 252 leading zero bits
  F2  x(kG)       column:x          256 bits
  …
  F5  hash160     column:hash160    160 bits, 96 leading zero bits
  F6  b58 payload column:b58_payload 192 bits, 64 leading zero bits
  lane 1: F4 xor F5  — digest → hash160 (the 96-bit pad shows as a flat delta)
  dataset: 3 rows × 6 columns (step rows to cycle)
  link: 1812 chars
  ! 6 stages are bound to 3 dataset rows (F1, F2, F3, F4, F5, F6) — step rows to cycle projects
  ! a canonical link would drop the dataset
```

Options: `--json` (machine-readable report + document summary + link),
`--check` (fail if the committed `.bitwave` output is stale, for a freshness
gate), `--base` (absolute URL to prefix the `#bw=` fragment).

Refusals are explicit, never silent truncation: an unsupported width, a stage
over the 16-frame cap, a lane outside the boot set, a missing dataset column, a
hex value wider than `N`, or a duplicate frame name all stop the build with a
message.

**The link caveat is real.** The canonical `#bw=` payload has a 2000-character
budget; a 3-row × 6-column dataset plus six provenance strings exceeds it, so
the link keeps the registers and drops the dataset (`datasetDropped`). Open the
`.bitwave` **file** when you want to step rows; share the link when you want a
fixed snapshot.

## 5. The worked demo

| artifact | what it shows |
|---|---|
| [`examples/btc-p2pkh.bitwave.json`](../examples/btc-p2pkh.bitwave.json) | the machine.py chain: toggleboard key → curve x/y → SHA-256 → RIPEMD-160 → Base58Check payload, 3 keys bound to dataset rows |
| [`examples/btc-avalanche.bitwave.json`](../examples/btc-avalanche.bitwave.json) | two runs compared: one key bit (1 → 3) vs 122 and 124 changed bits in the curve and digest lanes |

Open either with **project…** in the Source dock (the hidden `#projectFile`
input accepts `.bitwave`/`.json`), then use the stepper (`2 / 3`) to cycle
keypairs. Every dataset-bound frame re-settles in one clocked pass, and each
lane's `Z` recomputes from the new stages.

![P2PKH chain: six stages as free-frame waveforms, three XOR delta lanes](agent/btc-p2pkh.png)

![Avalanche: lane 1 flat (popcount 1), lanes 2–3 noise (122 and 124)](agent/btc-avalanche.png)

**Reading the padding.** A 160-bit digest in a 256-bit field is 96 leading
zeros, which draw as a flat line on the left of the waveform. That is not
noise: it is the true width of the stage, and it makes "this value is 160 bits"
visible. The same is true of the 200-bit Base58Check payload (64 leading zero
bits because the version byte is `0x00`).

**Reading the deltas.** XOR is the Hamming delta. In the avalanche document,
lane 1 (`k=1 ⊕ k=3`) reads popcount 1, while lanes 2 and 3 read 122 and 124:
one bit of input, about half the word of output. The frame cards make that
visible as flat vs noise before you read a single number.

## 6. For an agent

- The same document is accepted by `build_deeplink` (`--project`), so a
  generated file can be turned into a share link by the existing transport.
- The stage table is the thing to emit from a computation; the pipeline spec is
  the reusable mapping; the generated `.bitwave` is the artifact under version
  control (`--check` keeps it honest).
- `getState()` reports the stages as `freeFrames` (`hex`, `label`, `sourceNote`)
  and each lane's `Z` in `lanes[*].derived`; `stepDataset(n)` cycles rows.
- Keep `label`/`sourceNote` short and factual — they are what a reader has when
  the waveform is on screen and the computation is long gone.
